# P2P模型和C/S模型

| **C/S（客户/服务器）** | 明确区分**服务请求方（客户）**和**服务提供方（服务器）**，服务器总是打开、等待客户请求 |
| --------------- | ----------------------------------------------- |
| **P2P（对等连接）**   | 不区分客户与服务器，**每台主机既是客户又是服务器**                     |

CS模型：

| 角色      | 特征                                                 |
| ------- | -------------------------------------------------- |
| **服务器** | **总是打开**、有**固定 IP 和熟知端口**、集中提供资源、被动等待请求、处理能力强      |
| **客户**  | **主动发起**通信、IP 与端口通常**动态、不固定**、请求服务后即结束、之间**不直接通信** |

**通信方向**：客户主动 → 服务器被动响应（请求-响应模式）。
**优点**：集中管理、便于控制和安全策略实施、资源统一。
**缺点**：
- 服务器是**瓶颈**（用户增加，性能下降）；
- **单点故障**风险；
- **可扩展性差**、服务器成本高。


P2P模型

|特点|说明|
|---|---|
|**对等性**|每个节点既请求服务**又提供服务**|
|**分布式**|无中心或弱中心，资源分散在各节点|
|**可扩展性好**|**节点越多，系统总服务能力越强**（关键优势）|
|**节点动态**|IP、端口、在线状态都不固定|

**优点**：可扩展性强、鲁棒性高（无单点故障）、资源利用充分、成本低。**结点越多性能越好**
**缺点**：难以管理、安全性差、节点"搭便车"、内容版权难控制、依赖对等方在线。

# 电子邮件
## 一、电子邮件系统的三个组成部分

|组成|作用|
|---|---|
|**用户代理 UA**|用户与邮件系统的接口（Outlook、Foxmail 等）：撰写、显示、收发邮件|
|**邮件服务器**|系统的核心，**24 小时工作**；负责发送/接收邮件、维护用户的**邮箱（mailbox）**|
|**邮件协议**|发送用 **SMTP**，接收用 **POP3 / IMAP**|

| 协议       | 用途       | 方向          | 传输层     | 端口      |
| -------- | -------- | ----------- | ------- | ------- |
| **SMTP** | **发送**邮件 | **推（push）** | **TCP** | **25**  |
| **POP3** | **接收**邮件 | **拉（pull）** | **TCP** | **110** |

SMTP要点

| 项目   | 内容                                                    |
| ---- | ----------------------------------------------------- |
| 全称   | Simple Mail Transfer Protocol                         |
| 工作方式 | 命令/响应模式（如 `HELO`、`MAIL FROM`、`RCPT TO`、`DATA`、`QUIT`） |
| 局限   | **只能传送 7 位 ASCII 码**，不能直接传二进制、图像、中文                   |
| 解决   | 用 **MIME** 扩展                                         |
#### MIME（多用途互联网邮件扩展）

- **不是新协议**，而是对 SMTP 的**扩展**；
- 作用：把**非 ASCII 数据**（中文、图片、二进制文件）**编码成 7 位 ASCII 码**，让 SMTP 能传送；
- 关键字段：**Content-Type**（数据类型）、**Content-Transfer-Encoding**（编码方式）；
- 常用编码：**base64**（用于二进制）、**quoted-printable**（主要用于文本）。
**关系**：`SMTP + MIME` 才构成能传任意数据的邮件发送方案。


电子邮件 = 信封 + 内容
内容 = 首部 + 主体
电子邮件用户名只需要在**所属邮件服务器内唯一**，不必全球唯一。如 `zhangsan@163.com` 与 `zhangsan@qq.com` 同时存在。
RFC 822 规定，邮件内容的**首部和主体之间用一个空行分隔**——这是报文格式的硬性规定。


### HTTP协议

|项目|内容|
|---|---|
|全称|超文本传输协议（HyperText Transfer Protocol）|
|层次|**应用层**，使用 **TCP**，端口 **80**（HTTPS 为 443）|
|核心特性|**无状态**、面向事务|
|连接方式|HTTP/1.0 默认**非持久**；**HTTP/1.1 默认持久**|
## 报文格式

**请求报文**

```
请求行：  GET /index.html HTTP/1.1
首部行：  Host: www.test.edu.cn
          ...
空行：    ← 必须有！
实体主体：GET 通常无主体
```
**响应报文**

```
状态行：  HTTP/1.1 200 OK
首部行：  Content-Type: text/html
空行：
实体主体：<html>...</html>
```

> **首部与实体之间必须有一个空行**（高频考点）。


|方法|作用|
|---|---|
|**GET**|请求读取资源（最常用）|
|**HEAD**|只要首部，不要主体|
|**POST**|提交数据|
|PUT|上传/替换资源|
|DELETE|删除资源|


| 类别  | 含义        | 典型                          |
| --- | --------- | --------------------------- |
| 1xx | 信息        | 100 Continue                |
| 2xx | **成功**    | **200 OK**                  |
| 3xx | **重定向**   | 301 永久、302 临时、**304 未修改**   |
| 4xx | **客户端错误** | 404 Not Found、403 Forbidden |
| 5xx | **服务器错误** | 500、502、503                 |
## 连接方式与时间计算（高频）

|方式|特点|
|---|---|
|**非持久连接**（HTTP/1.0）|每个对象都要**新建 TCP 连接**|
|**持久连接非流水线**|复用一个连接，但**收到前一个响应才发下一个请求**|
|**持久连接流水线**|连续发出多个请求，不用等响应|

**时间计算（N 个对象，忽略传输时间）**：

|方式|总时间|
|---|---|
|非持久|**N × 2 RTT**（每个对象：建连 1 RTT + 请求/响应 1 RTT）|
|持久非流水线|**1 RTT + N × 1 RTT**|
|持久流水线|**1 RTT + 1 RTT**|

> **例**：1 个 HTML + 5 张图片（共 6 个对象）
> 
> - 非持久：6 × 2 = **12 RTT**
> - 持久非流水线：1 + 6 = **7 RTT**
> - 持久流水线：1 + 1 = **2 RTT**
