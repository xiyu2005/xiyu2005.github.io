# Task1

## 1. 目标

Task1目标是分析给定的 Flask Web 应用源码，找出其中存在的安全漏洞，并利用这些漏洞获取服务器的控制权，最终读取位于服务器根目录下的 flag 文件。

## 2. 漏洞分析

通过审计提供的 Flask 源码，我们发现了两个可以串联利用的关键漏洞：**SQL 注入 (SQLi)** 和 **服务端模板注入 (SSTI)**。

### 2.1 SQL 注入 (SQLi)

在源码的 `index` 视图函数中，可以看到以下代码：

```python
id = request.args.get('id')
# ...
query = f"SELECT username FROM users WHERE id = {id}"
c.execute(query)
```

这段代码直接将用户通过 GET 请求传入的 `id` 参数，使用 f-string 格式化到 SQL 查询语句中，没有进行任何的参数化查询或过滤。这导致了典型的数字型 SQL 注入漏洞。攻击者可以通过构造恶意的 `id` 参数来操纵 SQL 查询语句。

例如，攻击者可以传入 `id=0 UNION SELECT 'some_string'`，使得最终执行的 SQL 查询变为： `SELECT username FROM users WHERE id = 0 UNION SELECT 'some_string'` 由于 `id=0` 很可能不存在，查询将会返回 `UNION SELECT` 中我们指定的内容 (`'some_string'`)。

### 2.2 服务端模板注入 (SSTI)

在获取数据库查询结果后，源码使用 `render_template_string` 函数来渲染前端页面：

```python
if results:
    name = results[0][0]
# ...
template = ''' 
    <html>...<h3>Hello, %s !</h3>...</html> 
    '''% (name)
return render_template_string(template)
```

这里的 `name` 变量来自于上一步 SQL 查询的结果。由于我们可以通过 SQL 注入控制 `name` 变量的值，并且 `render_template_string` 会执行模板字符串中的 Jinja2 表达式，这就构成了一个典型的服务端模板注入漏洞。

如果我们可以将 `name` 的值设置为一个 Jinja2 payload，例如 `{{ 7*7 }}`，那么在页面渲染时，服务器会计算 `7*7` 的结果并返回 `49`，而不是字符串 `{{ 7*7 }}`。

### 2.3 攻击链：SQLi + SSTI 

通过将这两个漏洞串联起来，我们可以实现远程代码执行 ：

1. **注入点**：利用 `id` 参数的 SQL 注入漏洞。
    
2. **注入内容**：注入一个 `UNION SELECT` 语句，其内容是一个精心构造的 Jinja2 SSTI payload。
    
3. **执行点**：当 `render_template_string` 函数渲染我们注入的 payload 时，SSTI 漏洞被触发，从而在服务器上执行我们指定的代码。
    

## 3. 解题思路与脚本编写

### 3.1 核心攻击 Payload

为了实现 RCE，我们需要一个能够在 Jinja2 环境中执行 shell 命令的 SSTI payload。

```python
{{ self._TemplateReference__context.joiner.__init__.__globals__.os.popen('shell_command').read() }}
```

这个 payload 通过访问模板的内部对象和全局变量，最终调用了 Python 的 `os.popen` 方法，从而可以执行任意 shell 命令并读取其输出。

### 3.2 脚本编写思路

我们使用 Python 的 `requests` 库来编写自动化攻击脚本，主要逻辑封装在 `execute_command` 函数中。

1. **命令封装**: `execute_command(command)` 函数接收一个 shell 命令作为参数。
    
2. **Payload 构造**:
    
    - **SSTI Payload**: 将传入的 `command` 格式化到 SSTI 模板字符串中。这里有一个关键点：Python 的 `.format()` 方法会将 `{{` 转义为 `{`。为了得到最终的 `{{ ... }}`，我们的模板字符串必须写成 `{{{{ ... }}}}`。
        
    - **SQL Payload**:
        
        - 为了防止 SSTI payload 中的单引号破坏 SQL 语句的结构，我们需要将其中的每个单引号 `'` 替换为两个单引号 `''`，这是 SQL 中转义单引号的标准方式。
            
        - 将处理后的 SSTI payload 嵌入到 `0 UNION SELECT '...'` 语句中。
            
3. **发送请求**: 使用 `requests.get()` 方法，将构造好的 SQL payload 作为 `id` 参数的值发送给目标服务器。
    
4. **结果解析**: 使用正则表达式 `r'<h3>Hello, (.*?) !</h3>'` 从服务器返回的 HTML 响应中提取出命令执行的结果。
    
5. **自动化流程**:
    
    - 脚本首先调用 `execute_command("ls -la /")` 来列出根目录下的所有文件。
        
    - 从输出中，我们手动识别出 flag 文件名为 `f14g_i5_h3r3`。
        
    - 最终版本的脚本直接硬编码该文件名，调用 `execute_command("cat /f14g_i5_h3r3")` 来读取文件内容。
        
    - 将最终结果打印在控制台。

# Task2
#### **1. 实验目的**

本次实验旨在分析一个网络服务。根据题目要求，该服务接收 `.docx` 文件，其目标是读取服务器文件系统根目录下的 `/flag` 文件。本实验的核心任务是，通过构造恶意的 `.docx` 文件，利用该服务可能存在的文件解析漏洞，实现任意文件读取。

#### **2. 背景分析与初步假设**

根据题目给出的线索，我们进行了如下分析：

- **输入格式**: 服务处理 `.docx` 文件。
    
- **核心提示**: `.docx` 文件本质上是一个ZIP压缩包，其内部包含了大量的XML文件。
    
- **任务目标**: 读取服务器本地文件 (`/flag`)，且题目排除了远程代码执行（RCE）的需要。
    

基于以上分析，我们提出了核心假设：**服务器在解析上传的 `.docx` 文件时，其XML解析器存在XXE（XML External Entity，XML外部实体注入）漏洞。** 我们可以通过在 `.docx` 内的某个XML文件中插入恶意的实体定义，让服务器在解析时读取 `/flag` 的内容并将其呈现在返回结果中。

#### **3. 实验过程与步骤**

**阶段一：初步验证 (基于最小化Payload)**

1. **方法**: 编写一份Python脚本，使用 `pwntools` 库进行网络通信。脚本的核心功能是动态生成一个“最小化”的 `.docx` 文件。该文件仅包含构成一个有效 `.docx` 所必需的三个文件：`[Content_Types].xml`、`_rels/.rels` 以及被注入了XXE Payload的 `word/document.xml`。
    
2. **通信协议假设**: 采取了CTF挑战中常见的“大小前缀”协议，即先发送文件内容的总字节数，后发送文件本身。
    
3. **Payload内容**:
    
    XML
    
    ```
    <!DOCTYPE root [<!ENTITY xxe SYSTEM "file:///flag">]>
    <w:document>...<w:t>&xxe;</w:t>...</w:document>
    ```
    
4. **结果**: 执行脚本后，与服务器连接成功，数据也成功发送。但服务器立即关闭了连接，客户端未收到任何返回数据（0字节响应）。
    
5. **初步结论**: 首次尝试失败。失败的原因推测为：① 通信协议不正确；或 ② 服务器的解析器较为严格，我们构造的最小化 `.docx` 文件因缺少必要的元数据而被判定为无效文件，导致解析流程提前终止。
    
![[Pasted image 20250729235036.png]]
**阶段二：迭代排错**

面对首次失败，我们制定了两个方向的排错计划。

1. **排错方向A：调整通信协议**
    
    - **尝试**: 修改脚本，去除了发送文件大小的步骤，直接发送文件的二进制内容。
        
    - **结果**: 与阶段一相同，服务器仍然返回0字节并关闭连接。
        
2. **排错方向B：改进Payload结构 (模板替换法)**
    
    - **新假设**: 服务器需要一个结构完全合法的 `.docx` 文件才能进入易受攻击的解析流程。
        
    - **方法**: a. 首先，使用Word创建一个内容简单的 `template.docx` 文件，确保其格式完全合规。 b. 随后，升级Python脚本，使其能够读取这个`template.docx`模板，在内存中将其解压，用我们含有XXE Payload的 `word/document.xml` 替换掉模板中原有的同名文件，最后再重新打包成一个新的、结构完整的恶意 `.docx` 文件。
        
    - **遇到的问题**: 在实施此方案的初期，脚本报告 `zipfile.BadZipFile` 错误。经排查，原因是最初用于测试的模板文件是由macOS的非标准文本编辑器创建的，其后缀虽为 `.docx`，但实际并非标准的OOXML（ZIP）格式。在更换为由Google Docs生成的模板后，此问题得到解决。
        

**阶段三：最终测试**

在解决了Payload结构和模板文件格式的问题后，我们使用了结构最完善的Payload进行最终测试。

1. **测试3.1 (直接发送)**: 使用模板法生成的payload，直接发送。**结果**: 失败，仍为0字节响应。
    
2. **测试3.2 (大小前缀)**: 使用模板法生成的payload，并恢复“大小前缀”的通信协议。**结果**: 失败，仍为0字节响应。

#### **4. 实验结果与分析**

截至目前，所有尝试均未能成功从服务器获取响应，也未能读取到 `/flag` 文件。尽管最终目标未能达成，但整个过程排除了几种可能性。

当前结果表明，问题可能出在以下几个方面：

1. **漏洞类型判断错误**: 该漏洞可能不是常规的XXE，或者是一种“盲XXE”（Blind XXE）。盲XXE不会在当前响应中直接返回数据，而是需要通过带外通道（OOB）等更复杂的方式来提取信息。
    
2. **通信协议未知**: 服务器可能采用了更独特的通信协议，例如需要特定的认证头，或某种形式的交互式对话。
    
3. **存在安全防御**: 服务器可能部署了基础的WAF（Web应用防火墙）或安全逻辑，能够检测到XML中的 `<!ENTITY` 关键字或 `file:///` 协议，一旦发现便直接丢弃连接，不作任何响应。
    

#### **5. 总结与反思**

本次实验虽然未能完成最终目标，但完整地执行了一套“假设-验证-排错-迭代”的科学探索流程。我们从一个合理的XXE漏洞假设出发，通过编写代码实现了漏洞利用的尝试，并在遇到失败后，系统地分析了可能的原因，并逐一进行了排查和修正。

通过本次实验，我们验证了Payload结构完整性的重要性，并学会了如何排查和解决由文件格式不匹配导致的技术问题。虽然未能成功，但整个过程对于理解漏洞利用的复杂性和调试的系统性具有重要的实践意义。后续的探索方向可以集中在盲XXE的探测或使用更底层的网络工具（如`netcat`）进行手动协议探测。

# Task3
#### **摘要**

本次实验旨在通过对一个存在SQL注入漏洞的Web应用（Passcode+ 挑战）进行安全分析，最终获取后台Flag。实验过程采用“黑盒测试”方法，从零信息开始，通过一系列由浅入深的注入尝试，逐步揭示了目标的防御机制和漏洞利用方式。我们先后经历了**初始探测**、**标准UNION注入**、**时间盲注**，并对攻击脚本进行了多次迭代优化，最终成功构建了一套能够稳定、精确地从数据库中提取多行数据的攻击方案。尽管在交互结束时未获得最终Flag，但已经完整地探明了漏洞原理、防御策略及最终的利用途径。


#### **1. 实验目标**

1. 识别目标Web应用的注入点和类型。
    
2. 分析并绕过其部署的Web应用防火墙（WAF）或输入过滤器。
    
3. 利用SQL注入漏洞，从数据库 `passcodes` 表中提取一个或多个正确的 `passcode`。
    
4. 提交正确的 `passcode` 以获取最终的Flag。
    

#### **2. 实验环境与工具**

- **目标环境：** 靶机 (`127.0.0.1:52594`)，后端数据库为 MySQL。
    
- **主要工具：** Python 3
    
- **核心库：** `pwntools` (用于网络连接和交互)
    

---

#### **3. 探索方法与过程**

本次实验过程是一个典型的逐步深入、不断修正假设的迭代过程。

##### **阶段一：初始探测与WAF分析**

- **操作：**
    
    1. 发送正常字符串 `baseline_test_12345`，服务器返回空响应 `b''`，建立“失败”基准。
        
    2. 发送单个单引号 `'`，服务器返回 `HTTP 400 Bad Request`，表明SQL查询语法被破坏，**确认存在单引号字符型注入点**。
        
    3. 发送 `' OR 1=1 --`，服务器返回 `400 Bad Request`，推测 `OR` 关键字被过滤。
        
    4. 发送 `' union select 1 --`，服务器返回空响应 `b''`，表明 `union select` 组合被WAF拦截。
        
    5. 发送 `' UNION/**/SELECT 1 --`，服务器返回 `400 Bad Request`。这是一个**关键发现**：服务器返回了SQL语法错误而非WAF拦截响应，证明 `/**/` 成功绕过了对空格的过滤，让 `UNION SELECT` 关键字到达了数据库后端。
![[Pasted image 20250729234832.png]]
![[Pasted image 20250729234851.png]]
- **结论：** 目标存在字符型SQL注入，并部署了对 `OR`, `union select` 等关键字进行过滤的WAF。已找到WAF的一个绕过方式：使用MySQL的内联注释 `/**/` 代替空格。
    

##### **阶段二：标准UNION注入与盲注场景确认**

- **操作：**
    
    1. 基于阶段一的发现，编写脚本尝试进行标准UNION注入攻击。
        
    2. 脚本首先通过发送 `'' UNION/**/SELECT NULL, NULL, ...` 探测列数。
        
    3. **成功确定原始查询的列数为 1**。
        
    4. 随后尝试直接回显数据：`'' UNION/**/SELECT passcode FROM passcodes LIMIT 1 --`。
        
- **观察：** 尽管SQL语法完全正确，服务器返回的依然是空响应 `b''`。
    
- **结论：** 这是一个**盲注（Blind SQL Injection）**场景。即使注入查询成功执行，应用后端逻辑也不会将查询结果直接显示在页面上。必须转换思路，采用不能直接看到回显的注入技术。
    

##### **阶段三：时间盲注的初步尝试与陷阱分析**

- **操作：**
    
    1. 将攻击策略切换为时间盲注，利用 `SLEEP()` 函数根据条件的真假产生不同的响应时间。
        
    2. 构建了基于 `WHERE ... AND SLEEP()` 的payload，如：`... WHERE SUBSTR(passcode,1,1)='a' AND SLEEP(2) --`。
        
- **观察：** 脚本运行后产生了不合逻辑的结果（连续输出90多个'0'）。
    
- **结论：** 该方法存在严重缺陷。当 `SUBSTR()` 因超出字符串长度返回 `NULL` 时，`NULL='a'` 的比较结果也为 `NULL`（等同于FALSE），导致 `SLEEP()` 函数因“短路求值”而永不执行。脚本无法区分“字符错误”和“已达字符串末尾”这两种情况，在网络波动的干扰下产生了“假阳性”，导致无限循环。
![[Pasted image 20250729234914.png]]

##### **阶段四：构建稳健的时间盲注攻击脚本**

- **操作：**
    
    1. **引入 `IF(condition, true_action, false_action)` 函数**，这是时间盲注的最佳实践。Payload变为 `... IF(SUBSTR(passcode,1,1)='a', SLEEP(2), 'anything') ...`，逻辑更清晰且不受短路求值影响。
        
    2. **增加长度探测阶段**，在提取字符前，首先使用 `LENGTH()` 函数确定密码的准确长度。这为攻击设定了明确的终点，彻底解决了无限循环问题。
        
    3. 使用此优化脚本进行攻击。
        
- **观察：** 脚本成功、稳定地探测出第一行 `passcode` 的长度为1，内容为 `'0'`。
    
- **结论：** 已掌握对该目标的稳定、精确的单行数据提取方法。
    

##### **阶段五：多行数据遍历与最终方案**

- **操作：**
    
    1. 提交阶段四中获取的密码 `'0'`，服务器返回空响应，证明此密码无效。
        
    2. 回顾题目描述“有多行数据”，推断正确密码在表的后续行中。
        
    3. **修改 `LIMIT` 子句为 `LIMIT row_offset, 1`**，并用一个外层循环来遍历 `passcodes` 表中的每一行。
        
    4. 形成最终攻击流程：循环遍历每一行 -> 对该行进行长度探测和字符提取 -> 提交获取到的密码 -> 验证响应 -> 若失败则继续下一行。
        
- **观察：** 最终脚本成功启动，并重复了之前的发现：第一行的密码是'0'，且无效。脚本的逻辑已准备好继续探测第二行、第三行……

#### **4. 实验结果与分析**

- **漏洞类型：** 已确认目标存在基于时间延迟的、单引号字符型的**盲SQL注入**。
    
- **防御机制：** 目标存在一个中等强度的WAF，可被 `/**/` 注释绕过。应用后端逻辑不直接回显数据，有效防御了标准UNION注入。
    
- **数据库信息：** `passcodes` 表至少包含两行数据。第一行的数据是 `'0'`，但此密码并非获取Flag的正确凭证。
    
- **最终利用链：** `WAF绕过 -> UNION注入 -> IF函数时间盲注 -> 长度探测 -> 字符提取 -> 多行遍历`。这条利用链是针对此类场景的完整且可靠的攻击范式。
